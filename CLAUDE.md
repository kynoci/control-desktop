# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A cross-platform desktop **Control Desktop** remote-access app (RDP + VNC) built with **Tauri 2** (Rust backend) + **Vue 3 / TypeScript** (UI). Connection metadata lives in SQLite; passwords live only in the OS keychain, never in the DB.

## Commands

```bash
npm install            # first time only (also compiles ~300 Rust crates on first dev run, 5–10 min)
npm run tauri dev      # run the full desktop app with hot-reload (use this for development)
npm run tauri build    # build a release installer -> src-tauri/target/release/bundle/
npm run build          # type-check (vue-tsc --noEmit) + vite build of the frontend only
```

There is no test suite and no linter configured. `npm run build` is the only type-check gate — run it after frontend changes. For Rust-only changes, `cargo check` / `cargo build` inside `src-tauri/` is faster than a full `tauri dev` cycle. `npm run dev` (bare Vite, port 1420) serves the UI in a browser but Tauri `invoke` calls fail there — only useful for pure styling work.

## Architecture

Connection paths share one credential/DB layer. Clicking a connection card uses an embedded pure-Rust client chosen by the connection's `protocol`:

1. **Embedded IronRDP client (RDP, primary)** — `src-tauri/src/rdp.rs`. A pure-Rust RDP client (the `ironrdp` crates) that speaks RDP in a background tokio task, decodes the framebuffer, and streams it to a webview `<canvas>`. No external program required; works on all platforms.
2. **Embedded VNC/RFB client** — `src-tauri/src/vnc.rs`. A pure-Rust RFB client (the `vnc-rs` crate) built as a sibling of `rdp.rs`: same background-task / `Channel` / `CancellationToken` shape, same credential + DB layer. Used when `protocol === 'vnc'`. Supports None + VNC Auth only; requests RGBA pixels + ZRLE/CopyRect/Raw encodings (no Tight). See `plan-vnc.md` for the design and the spike that picked the crate.
3. **`mstsc.exe` fallback (Windows only)** — `connect_rdp` / `launch_mstsc` in `src-tauri/src/lib.rs`. Injects the password via `cmdkey` then launches Windows' native client in its own window. Triggered by the 🖥 button on a card (RDP connections only). Returns an error on non-Windows.

> Note: `README.md` is partly stale — it describes FreeRDP (Linux/macOS) and mstsc as *the* launch backends. The code has since moved to embedded IronRDP as the primary path; there is **no FreeRDP code** in the repo. Trust the source over the README here.

### Frontend ↔ backend contract

- **Tauri commands** (registered in `lib.rs` `run()` via `generate_handler!`): `save_password`, `get_password`, `delete_password` (keychain); `connect_rdp` (mstsc); `rdp_connect`, `rdp_input`, `rdp_resize`, `rdp_disconnect` (embedded RDP); and `vnc_connect`, `vnc_input`, `vnc_resize`, `vnc_disconnect` (embedded VNC). The frontend picks `rdp_*` vs `vnc_*` per the session's `protocol`.
- **Frame streaming uses a raw binary protocol over a Tauri `Channel`**, not JSON. Little-endian, first byte is a tag (see top of `rdp.rs` / `vnc.rs` and `handleFrame` in `App.vue` — they must stay in sync):
  - `0` init: `[0][width u16][height u16]` → frontend sizes the canvas. (both)
  - `1` strip: **retired.** The legacy RDP path used to widen every dirty rectangle to the desktop width so the pixel data was contiguous in `DecodedImage`; on a wide desktop that sent ~70x the bytes a small update needed (a caret repaint became 1390x20) and is most of why that path felt heavy. It now copies the rectangle out row by row and sends tag `3` like everything else.
  - `2` status: `[2][utf-8]` → human-readable status/error shown on the tab. (both)
  - `3` rect: `[3][x u16][y u16][w u16][h u16][rgba...]` → an arbitrary dirty rectangle drawn via `putImageData(…, x, y)`. Every pixel path uses it: VNC RFB updates, RDP Graphics Pipeline surface updates, and the legacy RDP path.
  - `6` ended: `[6][utf-8]` → the session stopped (error or clean close). Deliberately distinct from `2` so the UI can tell "still connecting" from "it stopped" without parsing the wording. (both)
  - `7` clipboard: `[7][utf-8]` → remote clipboard text mirrored into the webview. (RDP) Was tag `3` until EGFX landed; it collided with the rect tag, and since the rect branch matched first the clipboard branch in `handleFrame` was unreachable.
- **Input** flows back through `rdp_input` / `vnc_input` as JSON tagged events (`move`/`button`/`wheel`/`key`). The mouse events are protocol-neutral; only `key` differs: RDP uses **set-1 scancodes** (`src/scancodes.ts`), VNC uses **X11 keysyms** (`src/keysyms.ts`). Each map must mirror what its backend expects. `onKey` in `App.vue` branches on the active session's protocol.

### Connection organisation (folders & ordering)

- Connections live in a **folder tree** (`folders` table, `parent_id` self-reference; `connections.folder_id`). `NULL` = the root, shown as "Home".
- Folders and connections inside one parent share **a single `sort_order` sequence**, so drag-sorting can interleave them. `itemsIn(folderId)` in `App.vue` merges both tables into one ordered `Item[]`; `persistOrder()` rewrites `sort_order` as `0..n-1` after a drop.
- Drag & drop (HTML5 DnD, no library): a card's outer 25% edges mean *insert before/after*, the middle of a **folder** card means *move inside*. Breadcrumb crumbs, sidebar folder rows, and the grid background are also drop targets (all route through `moveInto`). `isDescendantOf` blocks dropping a folder into its own subtree.
- Deleting a folder **never deletes connections** — its contents are re-parented to the deleted folder's parent.
- The sidebar tree is rendered from `treeRows`, a *pre-flattened* list of `{item, depth, expanded}` — flattening avoids needing a recursive component inside the single-file `App.vue`.

### Session model

- The embedded client supports **multiple concurrent sessions**, one per UI tab. Each is keyed by a frontend-assigned `session_id` (incrementing integer, distinct from the DB connection `id`).
- Backend session state lives in `RdpState` (a `Mutex<HashMap<u32, SessionHandle>>` managed by Tauri). Each `SessionHandle` holds input/resize mpsc senders + a `CancellationToken`. Reconnecting on the same tab cancels and replaces the old session.
- In `App.vue`, **canvas/ctx and per-session runtime are deliberately kept out of Vue reactivity** (plain `Map<number, Runtime>`), because proxying a canvas breaks rendering. Only `sessions` (tab metadata) and `connections` are reactive refs.
- Thumbnails are captured off the frame path (`scheduleIdle` → `requestIdleCallback`): the JPEG encode plus the `localStorage` write costs several milliseconds, and doing it inline showed up as a hitch every few seconds. The timestamp is stamped when the capture is *queued*, so a slow encode cannot queue a second one.
- Thumbnails: the canvas is periodically snapshotted to a JPEG data URL and cached in `localStorage` under `thumb:<connId>`, shown on the connection cards.

### Connection internals (`rdp.rs`)

- `establish()` does one full attempt: TCP → RDP negotiation → TLS upgrade → CredSSP/NLA. `run_session()` wraps it in a **bounded reconnect loop** (`MAX_ATTEMPTS = 6`) to tolerate the post-auth "handoff disconnect" some servers (e.g. GNOME Remote Login) issue — see `is_handoff_disconnect`.
- **NLA/CredSSP is enforced** (`enable_credssp: true`, `autologon: true`) so stored credentials log straight in. Only **NTLM** is supported — Kerberos/KDC round-trips fail fast (`NoKdcNetworkClient`).
- **TLS certificate verification is intentionally disabled** (`danger::NoCertificateVerification`) — RDP hosts present self-signed certs; this mirrors clicking through the mstsc/FreeRDP warning on a trusted LAN.
- Server-initiated resize (`DeactivateAll`) is handled by `reactivate()`, which reruns the activation sequence and rebuilds the framebuffer at the new size. Client-initiated resize goes through the Display Control dynamic channel (`encode_resize`).
- **The Graphics Pipeline (EGFX) channel is mandatory for some servers.** `gnome-remote-desktop` (Ubuntu) has *no* legacy bitmap output path: without the `SUPPORT_DYN_VC_GFX_PROTOCOL` capability bit **and** a live EGFX channel it authenticates you and then closes the connection during capabilities exchange, logging "Client did not advertise support for the Graphics Pipeline". The client side of that shows up only as `ServerDeactivateAll` followed by a Disconnect Provider Ultimatum (`UserRequested`) — which looks exactly like a session handover, so don't be fooled by `is_handoff_disconnect`. `src-tauri/src/egfx.rs` implements `GraphicsPipelineHandler`, turning surface updates into tag-3 rect frames; `ironrdp-egfx` owns the channel state machine and `FrameAcknowledge`. No H.264 decoder is configured (the `openh264` features need a C toolchain), so the crate negotiates a non-AVC capability set.
- **`ironrdp-egfx` decodes almost nothing — `egfx.rs` fills the gap.** The crate decodes only `Uncompressed` and `Avc420`; per its own docs every other codec goes to `on_unhandled_pdu`, and each surface/cache command to a dedicated `GraphicsPipelineHandler` callback, so implementing them is the intended use. **`egfx.rs` is not per-server — once EGFX is up it carries the whole screen for every host** — but which subset a server uses varies wildly, so it must cover the union. GNOME streams **RemoteFX Progressive** (`WireToSurface2`, only `trace!`d upstream); Windows sends UI, text and icons as **ClearCodec** (sometimes **Planar**) and moves already-sent pixels with `SurfaceToSurface` / `SurfaceToCache` + `CacheToSurface`. Missing any one leaves stale blocks on screen (on Windows 11 it was a white square over the sign-in UI). `egfx.rs` therefore owns a `ProgressiveDecoder`, a `ClearCodecDecoder` and an RDP6 `BitmapStreamDecoder` from `ironrdp-graphics` — all three exist for this purpose but are never wired up upstream. All are **session-lived and stateful** (differential progressive tiles keyed by `codec_context_id`; ClearCodec glyph/V-bar caches), so `DeleteEncodingContext` must drop that context — the crate dispatches it to `on_delete_encoding_context`, *not* `on_unhandled_pdu` — and `ResetGraphics` must reset everything.
- **Dirty rectangles are merged before they are sent, on both RDP paths.** `merge_rects` in `rdp.rs` folds a row of tiles into one rectangle and a block into one, leaves rectangles that do not share an edge alone (so a clock and a cursor do not repaint the screen between them), and past `MAX_MERGED_RECTS` treats the batch as a full redraw and sends its bounding box. The legacy path merges each `process()` output batch; EGFX merges per frame (below). Unit tests for the merge live in `rdp.rs` — the only tests in the app crate.
- **EGFX updates are batched per frame.** The protocol addresses the screen in small pieces (a progressive refresh of 1000x662 is 176 64x64 tiles), and one channel message per piece meant 176 `putImageData` calls per frame — visibly stuttery, with half-painted frames. `paint()` therefore composites into the surface framebuffer and records a dirty rect; `on_frame_complete` (EndFrame) merges those rects — a tile row folds into one, a tile block into one — reads them back out of the framebuffer and sends those. Rects that do not share an edge are *not* merged, so updating a clock and a cursor does not repaint the screen; past `MAX_MERGED_RECTS` the frame is treated as a full redraw and sent as one bounding box. Batching only switches on after the first EndFrame, so a server that never frames its updates still paints immediately rather than queueing forever. `egfx.rs` carries unit tests for the merge (the only tests in the app crate).
- **EGFX can be turned off per connection** (`connections.legacy_graphics`, "Legacy graphics" in the connection editor). It flows through `ConnectRequest` to `rdp.rs`, which then neither advertises `SUPPORT_DYN_VC_GFX_PROTOCOL` (via the vendored connector's `Config::enable_egfx`) nor registers the EGFX dynamic channel; the server falls back to legacy surface commands that `ironrdp-session` decodes itself, and `egfx.rs` never runs. **This is only viable against servers that still have a legacy path — Windows does, `gnome-remote-desktop` does not** (it closes the connection at Capabilities Exchange), so it defaults to off. It exists because `ironrdp-pdu`'s ClearCodec implementation has repeatedly proven untested against real Windows streams; it is the escape hatch when a Windows host renders wrong, not the preferred path (legacy RemoteFX is coarser and rules out H.264).
- **Every EGFX surface carries a local RGBA framebuffer** (`SurfaceInfo::pixels`), and every producer composites into it before the same pixels go to the canvas. That is what makes the copy commands implementable: `SurfaceToSurface`, `SurfaceToCache` and `CacheToSurface` reference pixels the server already sent, which a draw-and-forget client no longer has. The source rect is copied out first so an overlapping same-surface blit still reads the original pixels; cache slots remember their own size because `CacheToSurface` carries only destination points. Offscreen (unmapped) surfaces are composited but never drawn — Windows stages cache content in them; as a guard, if the server never maps *any* surface all surfaces count as visible, so a server that just draws still renders. `paint()` crops everything to the surface, which is also how full-size progressive edge tiles are handled. See `plan-egfx.md`.

### Connection internals (`vnc.rs`)

- `run_session()`: TCP → `VncConnector` (RFB handshake + auth) → a `tokio::select!` over `{cancel, input_rx, 16ms tick}`. **RFB is request-driven**: the tick drains `poll_event()` (non-blocking) and re-sends `X11Event::Refresh` so the screen keeps updating.
- **Auth: None + VNC Auth only** (the `vnc-rs` crate does the DES internally). Any other security type (VeNCrypt/TLS, RealVNC RA2, …) is detected via the crate's error string and surfaced as an actionable message (`map_connect_err`) — mirrors `rdp.rs`'s clear-error approach. Plain TCP, no TLS.
- **Pixels: request `PixelFormat::rgba()`** so rects arrive as `[r,g,b,a]` — forwarded straight to the canvas, no swizzling. A local RGBA framebuffer is kept only to service **CopyRect** (`VncEvent::Copy`), which references previously-drawn pixels.
- **Client-initiated resize works via a vendored `vnc-rs` patch.** Upstream 0.5.3 has no resize at all, so `src-tauri/vendor/vnc-rs/` adds the `ExtendedDesktopSize` pseudo-encoding (-308), the `SetDesktopSize` client message (251), `X11Event::SetDesktopSize`, and `VncEvent::DesktopResizeSupported`; every change is marked `PATCH (Control Desktop)`. **`SetDesktopSize` must never be sent until the server has sent an `ExtendedDesktopSize` rect** — RFB gives a server no way to skip an unknown client message, so one lacking the extension *drops the connection*. `run_session` therefore gates on `resize_supported` (set by `DesktopResizeSupported`) and, when unsupported, warns the user once instead of sending. Encodings requested: ZRLE/CopyRect/Raw (no Tight, which would yield JPEG sub-rects).
- See `plan-vnc.md` §3 for the spike findings behind these choices.

## Important constraints & gotchas

- **`src-tauri/vendor/ironrdp-connector/` is a patched local copy** of ironrdp-connector 0.10.0 (adds `Config::enable_egfx`, which gates advertising `ClientEarlyCapabilityFlags::SUPPORT_DYN_VC_GFX_PROTOCOL` — upstream hardcodes that bit with no way to opt out, and both answers are needed: GNOME requires it, while a Windows server that sees it abandons the legacy path), wired in via `[patch.crates-io]` in `Cargo.toml`. Don't delete it; remove only once upstream exposes this as a `connector::Config` knob. The crate's earlier patch — tolerate a Server Deactivate All PDU during capabilities exchange — landed upstream in 0.10 and is no longer carried locally.
- **`src-tauri/vendor/ironrdp-graphics/` is a patched local copy** of ironrdp-graphics 0.9.0. Its RemoteFX **Progressive** tile reconstruction (`TileState::reconstruct_to_rgba`) hand-rolled a plain BT.601 YCbCr conversion using `y + 128` and a 16-bit shift. RemoteFX's DWT output is scaled by 2^5, so the correct conversion offsets by `128 * 32 = 4096` and shifts by `16 + 5` — as the crate's own *legacy* RemoteFX path does by delegating to `yuv`'s RDP variant. Upstream's encoder is unscaled too, so its round-trip tests pass while every real server frame saturates (mid-tones to black, highlights to red). The patch makes the progressive path reuse `color_conversion::ycbcr_to_rgba`.
  Three further progressive fixes live in the same file, all found against Windows 11: (a) a tile `quality` byte of **0xFF is a sentinel meaning "full quality"**, not an index into the region's progressive quant table (MS-RDPEGFX 2.2.4.2.1.5) — Windows sends it with `numProgQuant == 0`, so indexing the empty table rejected the tile ("quant index 255 exceeds table length 0"); (b) a **missing CONTEXT block** no longer rejects the frame ("progressive stream missing CONTEXT block") — it falls back to another live context, then to reduce-extrapolate, as FreeRDP does; (c) `decode_bitmap` used `?` inside the tile loop, so **one bad tile discarded every other tile in the frame**.
  Its **ClearCodec** path is patched too: the RLEX subcodec is decoded locally (`decode_rlex_region`) instead of via `ironrdp-pdu`'s `decode_rlex`, which special-cases a single-entry palette by reading every byte as a run length. The segment header byte is always on the wire — with one palette entry the stopIndex field is just zero bits wide and suiteDepth takes all eight — so dropping it desynchronised the segment stream and the region overran its pixel count (`invalid rlex: suite exceeds region pixel count`, leaving Windows taskbar/icon rects stale). The local version follows FreeRDP's `clear_decompress_subcode_rlex` but stops at the region edge instead of rejecting the rect, and a failing subcodec region no longer fails the whole ClearCodec bitmap. Because the crate has no logging facade, partial decodes are recorded in `ClearCodecDecoder::take_diagnostics()`, which `egfx.rs` drains into the log. The **bands layer** is patched the same way: upstream reads SHORT_VBAR_CACHE_MISS with `shortVBarYOn` at bits 6..13 and `shortVBarYOff` at bits 0..5, where the wire (and FreeRDP) puts yOn in the low 8 bits and yOff at bits 8..13 — real Windows bands failed the yOff >= yOn check and the rect was dropped. Neither RLEX nor bands had upstream test coverage; the vendored copy adds some. Remove once fixed upstream.
- **`src-tauri/vendor/vnc-rs/` is likewise a patched local copy** of vnc-rs 0.5.3, adding client-initiated resize (see the VNC section above). All three vendored crates are wired in through the same `[patch.crates-io]` block. Grep `PATCH (Control Desktop)` to see every local change.
- Crypto uses the **`ring`** rustls backend (not aws-lc) specifically to avoid needing a C/NASM toolchain at build time. Keep it that way unless you're prepared to add that toolchain.
- The OS window frame is disabled (`decorations: false`); the title bar, tabs, and min/maximize/close buttons are custom HTML in `App.vue` using `data-tauri-drag-region` and `core:window:*` permissions.
- Any new Tauri command must be added to **both** `generate_handler!` in `lib.rs` **and** the relevant capability in `src-tauri/capabilities/default.json`, or the webview call is rejected.
- SQLite schema changes go through `tauri_plugin_sql` **migrations** in `lib.rs` `run()` (append a new `Migration` with the next version — never edit an existing one). DB file: `%APPDATA%\com.kynoci.remote\remote.db`.

## Debugging

The built `.exe` has no console. Use **F12 / Inspect Element** for the JS console, or read the log file at `%LOCALAPPDATA%\com.kynoci.remote\logs\Control Desktop.log` (Rust + JS logs append in real time). The `ironrdp_connector` target is pinned to `Debug` level so server disconnects/redirections are diagnosable.
